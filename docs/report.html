report

For: anyone who wants a runway per tool, right now — the core command, and the natural next stop after the homepage's --compact teaser.

The core command. report looks at the telemetry your coding agents already wrote to disk, works out a burn rate per tool, and tells you how long each budget lasts at that rate. Units are never mixed: Copilot premium requests, Claude Code tokens and Codex sessions each get their own runway, and the tool that runs out first is flagged as the binding constraint.

Try it

$ token-finops adapters                             # which data sources exist on this machine
$ token-finops report --compact --budget 20000      # one line per tool
$ token-finops report --tool copilot --budget 20000 --since 7d

adapters, report --compact, then a full Copilot report with runway.

What to notice: --compact is the version you can glance at — a bar, a percentage, a runway and a status word per tool. The full report adds the burn rate it derived and the assumptions behind it, so you can see why a runway is short rather than just being told it is. Numbers in this recording come from synthetic data; every command is real.

Scoping it to one tool

If you only care about one assistant, --tool keeps the output to a single line and skips scanning everything else:

$ token-finops report --tool claude_code --compact
Claude Code        [############--------]  61.0%  runway   1.9h  WARN

That single line is exactly what the status line integrations put in your prompt or status bar.

Reading the full report

Drop --compact to see the lines the summary is derived from:

Claude Code — window: 5h (resets 2026-09-05 12:29 UTC)
  budget:   [############------------------]  40.0%
  window:   [############------------------]  40.0% elapsed
  pace:     1.00 (on pace)
  burn:     20.0% per hour (from snapshots)
  runway:   3.0h vs 3.0h left -> OK

budget is how much of the allowance is used. window is how much of the reset period has elapsed — comparing the two gives pace (1.00 means "burning exactly as fast as the window is passing"; above 1.00 means you'll run out before the reset). burn is the rate the tool derived from your recent usage, and runway is what's left at that rate versus what's left in the window. The binding constraint line at the bottom of a multi-tool report is just this same runway number, picked out across every tool at once, because heterogeneous units (percent, AI credits, requests/day, dollars) are never added together — only compared as "which one runs out first".

Claude Code needs two snapshots

Anthropic subscriptions only expose a percentage of the rolling 5h/7d window through the status line, not a running total. collect-statusline (see status line) stores one snapshot per redraw; a burn rate needs at least two snapshots in the same window to derive a slope. Wire the hook, use Claude Code for a few minutes, then re-run report --tool claude_code — a report immediately after wiring the hook for the first time will show ?/UNKNOWN rather than a runway, which is expected, not broken.

--json, for scripts

report --json emits an array with one object per tool, ready for a CI check or your own dashboard:

[
  {
    "tool": "claude_code",
    "display_name": "Claude Code",
    "window": "5h",
    "unit": "percent",
    "used": 61.0,
    "allowance": 100.0,
    "used_fraction": 0.61,
    "time_fraction": 0.32,
    "pace_ratio": 1.9,
    "burn_per_day_avg": 12.4,
    "burn_per_day_ema": 14.1,
    "runway_days": 0.079,
    "days_left": null,
    "resets_at": "2026-09-14T18:00:00+00:00",
    "status": "WARN",
    "notes": []
  }
]

runway_days is null when the runway is effectively infinite (a tool with no allowance, or usage-only data). status is one of OK, WARN, CRITICAL, EXHAUSTED, UNLIMITED, UNKNOWN.
