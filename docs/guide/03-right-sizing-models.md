# 03 — Right-Sizing Models

There's a joke that goes around teams that route work by model: Haiku can do everything except handle git well. It's not really about git — it's shorthand for the actual failure mode of cheap models, which isn't "can't write code," it's "loses the thread on multi-step state that has to stay consistent across a long, branching task." Haiku-class models are excellent at bounded, well-specified work and unreliable at anything that requires holding a lot of implicit context — like a repo's history — in its head while making a decision. Know which kind of task you're handing it before you hand it over.

## The rule: cheap models for menial work

The routing principle is simple to state and easy to violate under deadline pressure: reach for the cheapest model that can reliably do a task, and reserve the frontier model for the work only it can do well — architecture decisions, anything that requires deep cross-file reasoning, review passes where a wrong call is expensive to unwind. Everything else — boilerplate, formatting, straightforward research, adapter scaffolding that follows an established pattern — belongs on a mid-tier or cheap model.

We applied this rule to the repository this guide lives in, and chapter 02's numbers show what happened when we didn't apply it consistently enough. Sonnet — the mid-tier model — wrote three of the tool adapters in `src/token_finops/adapters/`, following the pattern established by the first one. That's exactly the kind of task the rule is for: well-specified, pattern-matching work, no architectural judgment required. The frontier model (Fable) wrote the core — the data model, the runway/pace-ratio math, the dedup logic — the parts where a subtle mistake produces a wrong number in front of a user, not just ugly code.

The expensive part was neither of those. It was three frontier-model research sub-agents — dispatched to investigate vendor pricing structures, adapter data sources, and prior art — that together cost more in API-equivalent terms ($13.68 + $7.37 + $5.04 = $26.09) than every Sonnet call in the entire session combined ($14.94). Research is exactly the kind of task that *feels* like it needs the frontier model — it involves judgment about what's relevant — but a well-scoped research sub-agent running on a cheaper model, with a tighter brief and a smaller context window, would very likely have done just as well for a fraction of the cost. That's the concrete lesson from dogfooding our own tool: the rule was right, we just under-applied it to the sub-agent layer, which is easy to overlook because sub-agents don't show up as line items you notice while you're working — they show up afterward, in the audit.

## What "menial" actually covers

In practice, the safe-to-downsize bucket is: formatting and markdown polish, mechanical refactors with a clear before/after spec, generating test fixtures from an existing schema, summarizing a known-format log or transcript, and any adapter/boilerplate work that has at least one finished example to imitate. The unsafe-to-downsize bucket is: anything where the model has to *decide* the shape of the solution rather than fill it in, anything touching security-sensitive logic, and — per the joke — anything that requires accurately tracking a long, stateful history (a multi-commit git operation, a long-running negotiation between competing constraints, a review that has to remember what was said three files ago).

## When not to downsize

Don't downsize research, review, or anything where being wrong is expensive to detect. A cheap model that gets an adapter's field names slightly wrong produces a test failure — annoying, cheap to fix. A cheap model that gets a pricing assumption or a security review slightly wrong produces a plausible-looking answer that's wrong in a way nobody catches until it matters. The cost asymmetry, not the per-call price, is what should decide the routing — which is also why "the frontier model wrote the core" wasn't a luxury choice in this repo, it was the same rule applied correctly in the other direction. And don't downsize on the assumption that cheap models are always cheap: a mid-tier model asked to do a frontier-tier task tends to loop, retry, or produce output that needs a frontier-model review pass anyway — at which point you've paid for both models and gotten the slower path to the same answer.
