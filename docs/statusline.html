status line

For: anyone who wants runway ambient in a prompt, tmux bar, or desktop widget instead of run on demand.

status is report squeezed into one line, meant for a shell prompt, a tmux status bar, or a desktop bar — somewhere you will see it without asking. It prints the binding constraint: the tool closest to running out.

Try it

$ token-finops status --fresh --budget 20000   # bypass the cache and re-read telemetry
$ token-finops status --format tmux
$ token-finops status --format starship
$ token-finops status --format waybar

status in plain, tmux, starship and waybar formats — cached, and with --fresh.

What to notice: each format is the same data, escaped for a different consumer — tmux colour codes, a starship module, and a JSON object for waybar. The default run is served from a short-lived cache so putting it in a prompt costs nothing per keystroke; --fresh forces a real re-read.

Wiring it up

Drop the format your bar expects into its config — the full snippets for tmux, starship, waybar and the Claude Code status line are in docs/INTEGRATIONS.md and docs/TMUX.md.

Prometheus (node_exporter textfile collector)

--format prometheus writes the standard text exposition format — no daemon, no network from our side, just a file the textfile collector already watches:

$ token-finops status --format prometheus
# HELP token_finops_used_fraction Fraction of the tool's budget/quota used in the current window (0-1).
# TYPE token_finops_used_fraction gauge
token_finops_used_fraction{tool="claude_code"} 0.61
# HELP token_finops_runway_days Days of runway left at the current burn pace.
# TYPE token_finops_runway_days gauge
token_finops_runway_days{tool="claude_code"} 0.08
# HELP token_finops_status Current status per tool, one series per known status value (1 = active, 0 = inactive) so alerting rules can match a specific status without relying on absent-series semantics.
# TYPE token_finops_status gauge
token_finops_status{tool="claude_code",status="OK"} 0
token_finops_status{tool="claude_code",status="WARN"} 1
token_finops_status{tool="claude_code",status="CRITICAL"} 0
token_finops_status{tool="claude_code",status="EXHAUSTED"} 0
token_finops_status{tool="claude_code",status="UNLIMITED"} 0
token_finops_status{tool="claude_code",status="UNKNOWN"} 0

A tool with an unbounded runway (UNLIMITED status, or OK with no burn yet) has no token_finops_runway_days series at all — Prometheus's text format has no Infinity/NaN literal that survives scraping without silently breaking a < alerting rule, so the metric is omitted for that tool rather than emitted as a bogus number. Point a cron job or systemd timer — the same refresher pattern as everything else on this page — at the collector's watched directory:

# cron, every minute
* * * * * token-finops status --format prometheus > /var/lib/node_exporter/textfile_collector/token_finops.prom.$$ \
  && mv /var/lib/node_exporter/textfile_collector/token_finops.prom.$$ /var/lib/node_exporter/textfile_collector/token_finops.prom

The write-then-rename avoids node_exporter reading a half-written file. Like every other format, this is read-only against the cache — no new rescan behaviour, nothing written except what you redirect yourself.

One refresher, many widgets

status reads a cache (~/.token-finops/last.json) and only rescans your telemetry with --fresh, or when the cache is older than --max-age seconds (default 300). A Claude Code project directory alone can hold hundreds of MB of JSONL — report rescanning that on every keystroke of a shell prompt would be unusable. Keep the cache warm with one timer and let every widget (prompt, tmux, waybar, whatever else you wire up) poll the cache as often as it likes, for free:

$ token-finops status                     # served from cache, plain, binding tools only
$ token-finops status --max-age 0         # never rescans — always serve the cache as-is
$ token-finops status --fresh             # force a real re-read right now

The refresher itself lives in contrib/refresh/ (a small timer that re-reads on an interval); the tmux plugin is contrib/tmux/token-finops.tmux. Widgets can grey out stale data using stale_seconds from status --format json.

Desktop notifications on a status change

A status bar only helps if you are looking at it. status --notify fires a native desktop notification instead, but only when the binding constraint's status class actually changes — OK → WARN, WARN → CRITICAL, and just as importantly WARN/CRITICAL → OK so you find out you are back in the clear. It never fires twice for the same class, so it is safe to run from the same timer that refreshes the cache:

$ token-finops status --fresh --notify

The last-seen class is recorded in ~/.token-finops/notify-state.json; the first run only establishes that baseline and does not notify. The mechanism used depends on the OS:

  • macOS — terminal-notifier if it is installed, otherwise osascript -e 'display notification …', which ships with every macOS install and needs nothing extra.
  • Linux — notify-send (part of libnotify, already on most GNOME/KDE desktops).
  • Windows — New-BurntToastNotification if that (third-party) PowerShell module is installed, else a System.Windows.Forms.NotifyIcon balloon tip built from .NET types that ship with Windows. This path is best-effort: it was written from the documented API, not exercised on a real Windows machine.

If none of the above is available, --notify degrades to a silent no-op (at most a note on stderr) — status's normal output and exit code are unaffected either way.

Claude Code status line

Different mechanism, same cache directory: collect-statusline stores the rate-limit percentages Claude Code itself pushes into its status line, which is what makes a CC segment possible at all.

// ~/.claude/settings.json
{ "statusLine": { "type": "command", "command": "token-finops collect-statusline" } }

Letting the agent ask, instead of watching it yourself

A status line is passive: it tells you the runway, and you decide. The other half of the problem is the agent about to fan out six sub-agents on the most expensive model — it never looks at your tmux bar. So the same runway is also packaged as something the agent can call mid-task, before it spends:

  • Claude Code — a /runway skill, in contrib/claude-code/runway/. Copy the directory to .claude/skills/runway/ in a project, or ~/.claude/skills/runway/ for every project.
  • Codex CLI — the equivalent as a custom prompt, contrib/codex/prompts/runway.md. Drop it in ~/.codex/prompts/ and invoke it as /prompts:runway.

Both wrap the same thing — token-finops report --json, read for the binding constraint. You can type /runway yourself, but the useful case is the description being written so the model invokes it on its own initiative before a large fan-out, and then says "you have 1.9 h of your 5 h window left; this will likely exhaust it" instead of finding out afterwards. The design reasoning, and what the equivalent would look like for the other agents, is in docs/INTEGRATIONS.md §3.
